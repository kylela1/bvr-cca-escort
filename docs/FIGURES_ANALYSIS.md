## Figure 1 — Full-scale (10,000,000-timestep) baseline learning curve

![](fig1_full_scale_learning_curve.png)

**What it shows**: `my_first_run` (seed 42, no heuristic factors, unmodified reward), the full
10M-timestep run this project's baseline will be compared against. The gray line is the raw
per-update training signal (noisy); the orange line is the deterministic 15-episode periodic
evaluation reward with its standard-deviation band; dashed vertical lines mark the 5 automatic
checkpoint-rollback events that fired between steps 4.0M and 6.0M.

**Analysis**: Training is highly non-monotonic — evaluation reward swings by more than 100
points between adjacent checkpoints even late in training, and the rollback mechanism
triggered 5 times in a 2M-step window (steps 4.0M-6.0M) before the run stabilized into
sustained improvement, eventually reaching a best evaluation reward of +80.65 at step 7.4M
(`best_checkpoint/best_model_info.json`). This instability is consistent with Bieger's own
thesis finding that PPO training in this environment is characterized by high variance rather
than smooth convergence — and it directly motivates using the **best checkpoint**, not the
final one, as the representative model for any comparison (the final-step policy is not
reliably the best one). This run is the reference baseline your redesigned reward should be
compared against — not the shorter, 1-seed pilot runs described in Figures 2-4, which used a
different (`mostly-original`-branch) evaluation stack (see `PILOT_EXPERIMENT_RESULTS.md` §3).

## Figure 2 — Pilot comparison: best-checkpoint reward by configuration

![](fig2_best_reward_by_config.png)

**What it shows**: The best evaluation-checkpoint reward achieved by each of 5 pilot
configurations (baseline, and Bieger's thesis Factors B, D, E, and the combined A+C+D
configuration), 1 seed, 2,000,000 timesteps each.

**Analysis**: Only the combined ACD configuration crosses into positive reward (+3.56); every
single-factor configuration and the baseline remain negative. Factor E (action blending)
underperforms even the unmodified baseline (-31.7 vs. -21.4), replicating Bieger's thesis
finding that action blending violates PPO's on-policy assumptions and actively hurts training.
Factors B and D each modestly outperform baseline individually (-15.6 and -14.7 respectively),
but the gap between "any single factor" and "the combined configuration" is far larger than the
gap between the individual factors themselves — the benefit compounds rather than adding
linearly.

## Figure 3 — Pilot comparison: mission-outcome metrics by configuration

![](fig3_mission_outcomes_by_config.png)

**What it shows**: HVAA survival rate, red-kill rate, and blue (CCA) loss rate for each
configuration's best checkpoint, evaluated over 20 episodes.

**Analysis**: This is where the reward numbers in Figure 2 stop telling the whole story.
Baseline and Factor B both show **0% HVAA survival** — the escorted asset never reaches its
objective under either configuration, despite Factor B having a better raw reward than
baseline. ACD achieves the highest red-kill rate (45%) and a perfect 0% blue-loss rate (the CCA
is never destroyed), but its HVAA survival (25%) is *lower* than Factor D's (50%) — ACD trades
mission completions for survivability and lethality. No single configuration dominates on every
metric, which is itself evidence that a single scalar reward is struggling to capture what
"good performance" means in this task — precisely the gap this project's reward redesign
targets.

## Figure 4 — Raw PPO reward is an imperfect proxy for mission win rate

![](fig4_reward_vs_winrate_rank.png)

**What it shows**: Panel (a) re-expresses HVAA survival as an approximate win-rate proxy.
Panel (b) is a rank comparison: each configuration's position when ranked by best reward
(left) versus ranked by the win-rate proxy (right).

**Analysis**: This is the single most important figure for motivating the project. ACD ranks
**#1 by reward** but only **#3 by win-rate proxy**; Factor D ranks **#2 by reward** but **#1 by
win-rate proxy** — the two rankings visibly cross. If reward were a faithful proxy for mission
success, these rankings would be identical. They are not. This independently reproduces
Bieger's thesis Section 4.7.1 finding ("Reward Function Misalignment with Evaluation Metrics")
on an entirely separate, smaller-scale experiment — strong corroborating evidence that the
misalignment is a real, structural property of the existing reward function rather than an
artifact of one experiment.

## Figure 5 — The mechanism: the current reward pays more for loitering than for winning

![](fig5_reward_misalignment_illustration.png)

**What it shows**: Not measured data — an illustrative calculation using the *exact* reward
constants defined in `src/rl_files/env_factory.py`'s `REWARD_SHAPING_STACK` and
`src/rl_files/mission_tempo_shaping_perstep.py`, applied to three scenarios over a representative
~13,500-step episode.

**Analysis**: This figure identifies a specific, fixable mechanism behind Figure 4's
misalignment. `MissionTempoShapingPerStep` pays +0.006 every single step the HVAA is alive
after red is killed — accumulated over a long episode, this per-step trickle (+94.0 for
"kill red early, then loiter") outweighs the one-time reward for actually finishing the mission
(+39.0 for "kill red, then complete the mission efficiently"), because completing the mission
ends the episode early and cuts off further bonus accumulation. **The reward function currently
has a built-in incentive to delay mission completion.** This is a concrete, evidence-based
starting point for the redesign: rebalancing or capping this per-step term (recommended as
step one in `REWARD_SHAPING_STEPS_FORWARD.md` §4.2) is the most direct, quantifiable lever
available for closing the reward/win-rate gap shown in Figure 4.

## Resolved: `.zip` checkpoints were 0 bytes on this branch — root cause found and fixed

`my_first_run`'s `ppo_bace_blue_lead.zip` and `best_checkpoint/best_model.zip` were both 0
bytes, despite `new-code`'s `SkippableTrainPPO` fix (`rollback_eval_callback.py`) that was
specifically designed to eliminate the `model.save()` pickling crash this session found on
`mostly-original`. Root-caused afterward: `_create_scaled_lr_schedule()` (used by the rollback
mechanism's learning-rate decay) returned a closure that captured `self` — the callback
instance, which holds the live `eval_env` (a Godot socket) — reintroducing the exact same
"cannot pickle '_thread.lock' object" failure through a different path than the one
`SkippableTrainPPO` fixed. It only manifests once at least one rollback actually fires, which
none of this session's 2,000,000-timestep pilot runs did (`min_timesteps_before_rollback`
is 4,000,000) — only the full 10M-step `my_first_run` triggered it (5 times). Fixed by
capturing `min_lr` and `base_schedule` as plain local values instead of reading them off
`self` inside the closure; verified with an isolated reproduction before and after the fix
(see `REWARD_SHAPING_STEPS_FORWARD.md` for the full writeup). Not yet re-verified against a
real multi-hour rollback-triggering run — the next full-scale run will be the first live
confirmation.
